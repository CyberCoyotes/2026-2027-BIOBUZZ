## 1. Strategic context

Last season (DECODE) we used FTCLib command-based code. **This season we use the standard FTC SDK style instead**, for three reasons:

1. **It's what the FTC samples use.** Students can learn from `FtcRobotController/.../external/samples/` directly, without translating between two styles.
2. **It's easier to trace.** An iterative OpMode runs top to bottom every loop, with no scheduler deciding what runs when.
3. **It carries forward.** 2027-2028 moves FTC to SystemCore with more standard OpModes. Code habits built this year transfer.

We still organize the robot into **subsystems**, the same idea as in FRC: one class per mechanism. What we dropped is the framework (FTCLib's base classes, commands, and scheduler), not the idea. Our subsystems are plain Java classes.

### OpModes

- **Iterative OpModes** (`extends OpMode`), using `init()`, `init_loop()`, `start()`, `loop()`, and `stop()`.
- Start from the closest SDK sample (`BasicOpMode_Iterative`, `ConceptAprilTag`, …) and keep its section comments ("Code to run ONCE when the driver hits INIT", etc.).
- Always stop every motor in `stop()`.
- Put all tunable numbers at the top as `private static final` constants with a comment explaining how to change them. The Alpha test OpModes are the model.
- Annotate with `@TeleOp(name = "…", group = "…")` or `@Autonomous(...)`. Test OpModes use `group = "Testing"`.
- **Keep the Driver Station list short.** Once a subsystem is well tested, add `@Disabled` above its Alpha's `@TeleOp` line. Never delete the file. To bring it back, comment out the `@Disabled` line and redeploy. Currently hidden: `IntakeAlpha`, `ShooterPowerAlpha`, `ShooterRPMAlpha`, `ShooterRatioAlpha`, `ShotTableAlpha`, `TurretAlpha`, `VisionAlpha`. `PinpointAlpha`, `FiringSequenceAlpha` and `DriveAlpha` are shown for now (`DriveAlpha` only while the field-centric drive is tested, issue #54: put the `// ` back off its `@Disabled` line to hide it again).

### Subsystem classes (one per mechanism)

Each subsystem is a **plain Java class**: no base class (no FTCLib `SubsystemBase`), no commands, and no scheduler. It follows the idea in the SDK's `ConceptExternalHardwareClass` sample, split by mechanism. The difference from an FRC subsystem is that nothing calls `periodic()` for you: the OpMode's `loop()` calls `update()`.

**Naming:** every subsystem class name ends in `Subsystem` (`ShooterSubsystem`), and OpMode class names never do. That way, anywhere you see a class name, you can tell whether it's an OpMode or a subsystem. Use the full name for the variable too (`shooterSubsystem`).

```java
package org.firstinspires.ftc.teamcode.subsystems;

public class ShooterSubsystem {
    // Constants: tunable numbers, ALL_CAPS
    // Hardware: private motor/servo/sensor fields

    public ShooterSubsystem(HardwareMap hardwareMap) { /* get hardware, set directions and modes */ }

    // Actions the OpMode calls: setTargetRpm(), stop(), …
    // Questions the OpMode asks: isAtSpeed(), getRpm(), …

    public void update() { /* called once per loop() if the subsystem needs it */ }
    public void addTelemetry(Telemetry telemetry) { /* shows its own data */ }
}
```

Rules:
- **A subsystem owns its hardware.** Only `ShooterSubsystem` touches the flywheel motors, only `TurretSubsystem` touches the turret motor, and so on. OpModes call subsystem methods; they don't reach into the motors.
- **Constructor = setup.** It gets hardware from the `HardwareMap` and sets directions, modes, and zero-power behavior.
- **`update()` runs once per loop** for any subsystem with ongoing work (velocity checks, turret aiming, timers). The OpMode calls it; nothing calls it automatically.
- **State vs. status:** *state* is what the code told the subsystem to do (`targetRpm`, an enum like `IDLE / SPINNING_UP / READY`). *Status* is what sensors report (`getRpm()`, `hasTarget()`). Keep them separate so telemetry can show both.
- **No button references inside subsystem classes.** Gamepad handling lives only in TeleOp OpModes.
- **Sensors-only devices** (Limelight, Pinpoint) get plain wrapper classes too, e.g. `VisionSubsystem`, with an `update()` that reads the latest data once per loop.

### Where constants live

In FRC a `Constants` file is common. In FTC we keep each number with the class that owns it, because one file then explains the whole mechanism and a student never has to hunt for it. Ask "what does this number describe?":

| The number describes… | It lives in… | Examples |
|---|---|---|
| The **mechanism** | That mechanism's subsystem class, as `private static final` at the top | `DEFAULT_INTAKE_POWER`, motor directions, `FLYWHEEL_MAX_TARGET_RPM`, servo positions, soft limits |
| How a **test OpMode drives** a mechanism | That test OpMode | Dial step size, the Y/X/B/A preset powers, nudge step |
| Something **two or more classes** need, or the **field or robot** itself | A shared constants class (see below) | Hive and tag dimensions, camera and turret offsets |

Rules:
- **Don't copy a number into two files.** When a test OpMode finds a good value (the best intake power, a servo position), copy it into the subsystem's constant. The OpMode does not keep the real value, or the competition TeleOp would never see the tuning.
- **Hardware names live only in the subsystem that owns the hardware.** OpModes never call `hardwareMap.get`, so each name has exactly one home.
- **A shared constants class is created only when a second class needs the value.** Do not make a constants file with empty sections "just in case". Name it for what it holds (`FieldConstants`, `RobotConstants`). **Never call it plain `Constants`**: Pedro Pathing's setup puts its own `Constants` class in `pedro/`, and two classes with the same name are confusing to import.
- **Per-robot values** (practice bot, 11940, 22091 will differ) wait until the build flavors are set up (section 5).

### Typical TeleOp shape

```java
@TeleOp(name = "BIOBUZZ TeleOp", group = "Competition")
public class BiobuzzTeleOp extends OpMode {
    private DriveSubsystem driveSubsystem;
    private ShooterSubsystem shooterSubsystem;

    @Override public void init() {
        driveSubsystem = new DriveSubsystem(hardwareMap);
        shooterSubsystem = new ShooterSubsystem(hardwareMap);
    }

    @Override public void loop() {
        // 1. Read sensors (vision.update(), odometry, …)
        // 2. Read gamepads and decide what to do
        // 3. Tell subsystems what to do, then call their update()
        // 4. Telemetry
    }

    @Override public void stop() {
        shooterSubsystem.stop();
        driveSubsystem.stop();
    }
}
```

Keep that four-step order in every TeleOp `loop()`.

### Autonomous

- **Pedro Pathing 3** for paths. Follow Pedro's example pattern: an iterative OpMode with `follower.update()` in `loop()` and a `pathState` switch that moves from step to step. Use an `enum` for the steps. Pedro's docs recommend their command library "Ivy" for this; we do **not** use it (no command-based code). Rules and a template: `TeamCode/docs/pedro-setup-and-auto-guide.md`.
- Auto uses the **same subsystem classes** as TeleOp, **except the drivetrain**. Pedro's `Follower` drives the four drive motors in Auto, and only one class may control a motor, so `DriveSubsystem` is for TeleOp and Pedro drives in Auto. Never use both in one OpMode. Pedro's motor names and directions in its `Constants` must match ours. If we later want Pedro path-following inside TeleOp (a lower priority), `DriveSubsystem` would wrap the `Follower` and keep the same public methods, so TeleOp OpModes would not change.

## 3. MUST NOT: anti-patterns

- No FTCLib, no commands, and no schedulers. No base class like `SubsystemBase`. (Plain subsystem classes are fine and expected.)
- No lambdas, streams, or anonymous classes. Write the loop out.
- No `sleep()` or blocking waits inside `loop()`. Use `ElapsedTime` timers instead.
- No gamepad reads inside subsystem classes.
- No two classes controlling the same motor.
- No magic numbers buried in code. Make every tunable value a named constant.
- Don't use the BIOBUZZ AprilTags to locate the robot on the field. They move with the hive; use Pinpoint for position and the tags only for aiming (see `TeamCode/docs/biobuzz-hive-apriltag-geometry.md`).

### FiringSequence (`subsystems/FiringSequence.java`) and `FiringSequenceAlpha`: code written, not yet tested on the robot

- **What it is:** a plain class with **no hardware and no gamepad** (like `ShotTable` and `HiveBearingMemory`, so its name does not end in `Subsystem`). It is the steps of one **volley**: wait until ready, open the gate, feed the balls one at a time, close the gate. It is nearly the sequence `ShootAndParkAuto` works out for itself (the Auto still has its lift step, see the numbers below). The design (hold to fire, a pre-rev toggle) was approved by the coach on 2026-11-09 and is written in issue #63.
- **How an OpMode uses it:** once per loop, **after** `shooterSubsystem.update()`, call `update(fireHeld, readyToStart, flywheelAtSpeed)`, then read `getGateCommand()` (NONE = not mine, use the manual gate buttons; CLOSE / OPEN = send it to `ShooterServoSubsystem`), `ownsIntake()` and `wantsIntake()`. The OpMode, not the class, decides what "ready to start" means (flywheel at speed, the turret aimed by the **camera's `tx`** (not by `TurretSubsystem.isOnTarget()`, see the turret notes), and in TABLE mode the camera sees the hive right now). `ShooterServoSubsystem` and `IntakeSubsystem` still own their hardware.
- **Steps (changed after the coach's review: feed until released):** `WAIT_FOR_READY` (gate CLOSED, the intake is still the driver's) -> `FEED` (gate OPENED, and it **stays open until the button is released**; there is no timer; the intake runs **only while the flywheel is at speed AND the turret is aimed**, so it pauses by itself when either is lost). **Letting go at any step ends the volley:** the gate is closed once and the intake goes back to the OpMode. The gate stays open during the feed on purpose (closing it per ball would add the servo's travel time to every ball). `update()` now takes a fourth answer, `turretAimed` (the OpMode passes the same turret answer it used for `readyToStart`); `getIntakePauseReason()` says why the intake is paused ("flywheel not at speed", "turret not aimed" or both) and `getPausedSeconds()` adds the paused time up for the screen. **No "one volley per press" and no `FEED_SECONDS`** (the coach: the balls are light and show no noticeable RPM dips, and the old rules got in the way of lifting the last ball). **An optional feed limit** stays for the Auto, which has no button to release: `setMaxFeedSeconds(seconds)` (default `NO_FEED_LIMIT`, 0). When it runs out the gate CLOSES and the step becomes `DONE`, which waits for the release (so it cannot fire again by itself); the TeleOp never sets one, so `DONE` never happens there. **The LIFT step was removed (issue #63, after the first review):** the gate used to go LIFTED for 0.5 s with the intake on, to push the last ball in, but its timing was off and the last ball got wedged. **The operator now lifts by hand:** the gate's OPENED position is **between** LIFTED and CLOSED, and with the gate staying open, holding **Y** during the feed lifts it (the OpMode, not this class, returns it to OPENED on release). A ball that is half way through when the gate closes at the end could still jam: watch for it. The gate closed **gently** when this was written (that was later removed, see `ShooterServoSubsystem`), which should push a single ball aside instead of slamming it, **and the intake reverses by itself while it closes** (decided in the OpMode, not in `FiringSequence`: after DONE or an abort the sequence no longer owns the intake, so the OpMode's own gate-closing rule takes over).
- **No ball sensor:** the class cannot count balls. It counts **flywheel dips** (about one per ball, **if** the balls are heavy enough to cause a dip; the coach says they are not noticeable) and keeps a log of the last volley (seconds to ready, total seconds, result, dips, paused seconds), shown by `addTelemetry()`. A ball sensor in the chute would let a later version stop the feed by itself.
- **Numbers (all at the top):** `INTAKE_WAITS_FOR_SPEED` true, `INTAKE_WAITS_FOR_AIM` true, `NO_FEED_LIMIT` 0 (the feed limit is optional, set by `setMaxFeedSeconds`). `ShootAndParkAuto` has its own `FEED_SECONDS` 3.0 (a separate copy) and will pass a limit like it when it switches to this class. `ShootAndParkAuto` still has its own copy of the logic, **including its `LIFT_LAST_BALL` step and its own `GATE_LIFT_SECONDS`**, until its robot test confirms the timings, then it switches to this class (issue #63, session 3). **`[CONFIRM]` whether the Auto drops its lift too:** it has the same timing problem.
- **Test OpMode:** `FiringSequenceAlpha` ("Firing Sequence - Alpha", group Testing, gamepad1 only, no drive: move the robot by hand). **Right Trigger (hold)** fires a volley, **D-pad Up** toggles **PRE-REV** (wheels spin without firing, shown big on the screen), **Right Bumper** intake (pick up), **Left Bumper** reverse (jam), **X / B / Y** manual gate (**only when no volley runs**), **Back** TABLE / DIAL speed source, **START** alliance. The turret tracks the hive all the time. The flywheel target is frozen during FEED and DONE, and it only changes when the wanted RPM moves more than `RPM_CHANGE_DEADBAND` (10). Intake priority: jam reverse, then the gate-closing reverse, then the sequence, then the driver's button. **Y (hold)** lifts the gate (during a feed it returns to OPENED when let go; between volleys it closes). The header has the 10-step test order.

### ShooterSubsystem (`subsystems/ShooterSubsystem.java`)

- **Hardware:** `flywheel` is a goBILDA 5203 series **1620 RPM (3.7:1)** motor (changed from 6000 RPM on the `change-shooter-motors` branch). `hood_wheel` is still a goBILDA 5203 series 6000 RPM (1:1) motor, confirmed by the coach. Both have encoders plugged in, belt driven and believed to be 1:1 `[CONFIRM]`.
- **Different motors, different numbers (not tested on the robot yet):** `ShooterSubsystem` now has a ticks per rev, a motor top speed, and a max target RPM **for each wheel**. Flywheel: **103.8** ticks per output rev (spec sheet `5203-2402-0003`: 28 at the encoder shaft, 103.8 at the output shaft), 1620 RPM top speed, **1458 RPM max target** (90%). Hood wheel: 28 ticks per rev (spec sheet `5203-2402-0001`), 6000 RPM, 5400 RPM max target. `getMaxTargetRpm()` was replaced by `getMaxFlywheelTargetRpm()` and `getMaxHoodWheelTargetRpm()`. The encoder is on the motor shaft (before the gearbox), so the speed at full power is about 2,800 ticks/sec on **both** motors. The numbers are not in doubt (they come from the spec sheets), but a full-power run in `ShooterRPMAlpha` is a quick sanity check for wiring and config mistakes: the hood wheel should read about 6,000 RPM and the flywheel about 1,500 to 1,620 RPM.
- **Hood wheel ratio:** `HOOD_WHEEL_RATIO` is **2.0** (hood wheel RPM / flywheel RPM), the best value found in robot testing so far. `setTargetRpm()` uses it, and `BiobuzzTeleOp` starts its ratio dial at the same number. The **flywheel** now hits its limit first: it tops out at **1458 RPM** (`FLYWHEEL_MAX_TARGET_RPM`), where the hood wheel only needs 2916 RPM, far under its own 5400 RPM limit.
- **Control:** speed control in RPM (`setTargetRpm()` / `setTargetRpms()`). `setPower()` is open loop, for tests and clearing jams. `stop()` coasts (never commands a speed of 0).
- **States:** `IDLE`, `OPEN_LOOP`, `SPINNING_UP`, `READY`. `isAtSpeed()` is true only in `READY` and is the shooter's half of the firing gate. The turret's on-target check is the other half.
- **Test OpMode:** `ShooterRPMAlpha`. Its Right Trigger button runs the full-power encoder sanity check (see above).
- **Ratio test OpMode:** `ShooterRatioAlpha` finds the best `HOOD_WHEEL_RATIO` (hood wheel / flywheel). **It uses speed control (RPM)**, now that the flywheel and hood wheel encoders are connected. B/A turn the flywheel RPM dial (100 RPM steps), D-pad Left/Right turn the ratio dial (0.05 steps), Y/X start and stop the shooter, and hood wheel RPM = flywheel RPM x ratio. It warns CAPPED when the hood wheel target is over `ShooterSubsystem.getMaxTargetRpm()`, shows the measured ratio, and records the lowest RPM each wheel hit after reaching speed (Back resets it). Printable student sheet: `TeamCode/docs/hood-wheel-ratio-test-sheet.html` (and a `.pdf` copy). The old plain-POWER version is saved in git (commit `88c7669`), with its sheet `hood-wheel-ratio-test-sheet-power.html`, in case the encoders ever stop working.
- **At-speed tolerance is 25 RPM** (was 100) because the shooter gate will only open on `isAtSpeed()`. **Both** wheels must be within it, and one reading outside it drops READY at once. `[CONFIRM]` on the robot: if the RPM readout wanders more than about 15 RPM while steady, READY will flicker. Then fix the speed reading or the PIDF, don't loosen the tolerance without asking.
- **`isFlywheelAtSpeed()` (flywheel only, not tested on the robot yet):** true when the **flywheel alone** has been within the same 25 RPM for the same 0.15 s. `isAtSpeed()` (both wheels) is **unchanged**. It exists because both-wheels took about 4 s in the first Auto test: the hood wheel has 28 counts per rev against the flywheel's 103.8 and runs about twice as fast, so its reading is much noisier (see the hood wheel issue, #62). `FiringSequenceAlpha` and the firing sequence use it and show the hood wheel's error. The coach decides which one the TeleOp's "OK to shoot" uses.
- **Possible TeleOp problem (not confirmed):** `setTargetRpms()` treats ANY change of target as "start over" (READY drops, the hold timer restarts). In TABLE mode `BiobuzzTeleOp` sets the flywheel target from the table every loop, and the camera's `ty` wobbles a little, so the target may change every loop and READY may never hold. `FiringSequenceAlpha` only changes the target when it moves more than `RPM_CHANGE_DEADBAND` (10 RPM). **Handled in the TeleOp since #63 session 2:** `BiobuzzTeleOp` freezes the flywheel target and the ratio during FEED, LIFT and DONE and uses the same `RPM_CHANGE_DEADBAND` outside them. Still check it on the robot (#63, #62).
- **RPM smoothing (not tested on the robot yet):** the Hub's speed reading jumps about ±20 RPM from loop to loop at 1300 RPM (a heavy flywheel does not really change speed that fast, so the jump is mostly reading noise). `update()` now blends each reading into a running average (an exponential low-pass filter, `RPM_FILTER_TIME_CONSTANT_SECONDS`, starts at **0.10**). `getFlywheelRpm()`, `getHoodWheelRpm()`, the READY check and the screen RPM use the smoothed value. The raw ticks/sec lines on the screen are **not** smoothed. Tradeoff: a bigger number is steadier but can hide or delay the real dip when a ball goes through, so lower it if READY stays on during a shot. Set it to 0.0 to turn smoothing off.
- **Starting guesses to tune on the robot:** the hold time (`AT_SPEED_HOLD_SECONDS`), `FLYWHEEL_MAX_TARGET_RPM` and `HOOD_WHEEL_MAX_TARGET_RPM`, the PIDF numbers (the Hub's built-in values are used until `USE_CUSTOM_PIDF` is turned on), and the preset RPMs in `ShooterRPMAlpha`.
- **Not in this class:** the distance-to-RPM shot table (a separate class later), feeding, and anything that reads a gamepad.

### ShooterServoSubsystem (`subsystems/ShooterServoSubsystem.java`): code written, not yet tested on the robot

- **Hardware:** `shooter_servo`, a goBILDA dual mode 300° torque servo. It acts as a **gate** with **three positions**: CLOSED (holds the balls back so balls can be loaded into the shooter), OPENED (lets a ball pass into a ready flywheel and shooter), and LIFTED (lifts to push the last ball into the shooter). Set it to **positional** mode with the goBILDA Servo Programmer, and configure it as a plain "Servo" on the Driver Station.
- **Separate from `ShooterSubsystem`** so the flywheel tests still run on a robot where the servo is not configured yet.
- **States:** `CLOSED`, `OPENED` and `LIFTED` (renamed from `LOADING` and `SHOOTING` when the third position was added). A servo reports no position, so this is only what we commanded. `isAtPosition()` is a **time guess** (`SERVO_TRAVEL_SECONDS` since the last command), and is the gate's half of the future firing gate.
- **Methods:** `goToClosed()`, `goToOpened()`, `goToLifted()` (all instant), `toggle()` (flips CLOSED / OPENED only), `nudgePosition()` (for finding positions), `getState()`, `isAtPosition()`, **`isClearingChute()`**, `addTelemetry()`. It starts `CLOSED` when constructed (R103.B allows pre-positioning servos at INIT). **Instant close and the intake-reverse timer (code written, not yet tested on the robot).** Every move is instant, at the servo's top speed (set by the servo type and the angle it turns). The slow "gentle close" from issue #63 (`goToClosedGently()`, `update()`, `GENTLE_CLOSE_...`) was removed: it only helps when it is slower than the servo's own top speed, and the coach wanted a faster close. **`isClearingChute()`** is true for `CLOSE_REVERSE_SECONDS` (0.50) after the gate is commanded to close from OPENED or LIFTED (false if it was already closed, and it ends at once if the gate is told to open or lift). `BiobuzzTeleOp` and `FiringSequenceAlpha` run the intake backward while it is true (see the TeleOp notes). **It is a timer we tune, not a measurement:** a servo cannot report its position. **`[CONFIRM]`:** play with `CLOSE_REVERSE_SECONDS` on the robot with a ball left in the chute. ### TurretSubsystem (`subsystems/TurretSubsystem.java`): code written, not yet tested on the robot

- **Hardware:**
  - `turret_motor`: goBILDA 5203, **435 RPM (13.7:1)**, power on the port's power connector.
  - **For now the turret uses the motor's built-in encoder** (**384.5 counts per output-shaft revolution**, which is 28 × 13.7, per spec sheet `5203-2402-0014`), plugged into the port's encoder connector. **Later** the REV Through Bore Encoder (incremental/quadrature, **8192 counts per revolution**, on its own 16T pinion on the ring gear) can go in that same connector instead; change `ENCODER_TICKS_PER_REV` in `TurretSubsystem` when it does. There is **no separate `turret_encoder` config entry**: we have 8 motors and the two hubs have exactly 8 motor ports. The code reads it with `turretMotor.getCurrentPosition()`. The Control Hub cannot read the Through Bore's absolute pulse output.
  - **Direction coupling:** because they share a port, `setDirection()` reverses the motor and the encoder count together. `INVERT_ENCODER_READING` fixes the encoder's sign in software.
  - `turret_home_switch`: REV magnetic limit switch. It is **active-low**: it reads LOW when a magnet is near. Confirm on the robot with telemetry. **Configure it as a "Digital Device"** in the Driver Station, not "REV Touch Sensor": the SDK's touch-sensor class is not a `DigitalChannel`, which is what our code reads.
- **Gearing:** both spur gears (motor pinion and encoder pinion) are 16T. The ring gear is believed to be 48T `[CONFIRM]`. So the encoder shaft turns 3 times per turret revolution, which is `ticks per rev × (ring teeth / 16) / 360`. With the motor's built-in encoder (384.5) that is about **3.2 ticks per turret degree** (0.31° per tick). With the Through Bore (8192) it would be about 68.3. Cross-check by turning the turret by hand through a marked 90°.
- **Angle convention:**
  - **0° is the home switch, and it points at the intake direction** (straight ahead).
  - Angles are **signed**, and the travel is about 270° (±135°). The 90° dead zone is directly behind, opposite the intake.
  - **Positive is counterclockwise viewed from above** (turning left). This matches Pinpoint and Pedro Pathing heading, so `shooterFieldHeading = robotHeading + turretAngle`.
  - Soft limits are **±120°**, 15° inside the range, so the turret has room to coast before the cables or frame.
- **Zeroing:**
  - At power-up the turret is placed by hand **on the switch**. INIT telemetry warns if the switch is not active. There is no motion at INIT (G304, G403).
  - During a match, the switch turning on resets the encoder count to zero (0°). To avoid repeated re-zeroing while hovering at the magnet's edge, it re-arms only after the turret has moved about 10° away.
  - The hub keeps encoder counts between Auto and TeleOp, so nothing is stored in a static field. `isZeroConfirmed()` is false until the switch has been crossed once.
- **Control:** our own P controller (D added only if it oscillates) on the angle error, with a small friction kick, a max power clamp, and soft limits that cut power pushing past a limit. **Feedforward:** `setFeedforwardPower(power)` adds an extra push on top of position control so the turret can follow a spinning robot (position control only pushes once the turret is already off target, so on its own it always trails a spin). It **lasts one loop** (`update()` clears it, so a stale value can never keep the turret moving), it also works inside the "close enough" band, and the max power and soft limits still apply to the total. If you turn `KD` on while using it, `KD` pushes against the following motion. The motor `FLOAT`s until the first command (so the turret can be placed on the switch by hand during INIT), then uses `BRAKE` to hold position. `stop()` floats again. **Do not gate anything on `isOnTarget()` while auto-align is running:** its 1.5 degree tolerance is bigger than auto-align's 1.0 degree re-aim threshold, and every `setTargetAngle()` with a new value (auto-align gives one almost every loop, because `tx` jitters) clears the settle timer, so `isOnTarget()` can stay false while the turret is perfectly well aimed (see the firing sequence notes). **`ShootAndParkAuto` still does this** (`WAIT_FOR_SPEED` waits for `isOnTarget()` and aligns with the same 1.0 degree threshold), so it can stall the same way and then skip the shot after its timeout. Left alone on purpose until session 3 of #63.
- **Soft limits are ON at ±120°** (`SOFT_LIMITS_ON = true`, `MIN_ANGLE_DEGREES` / `MAX_ANGLE_DEGREES` in `TurretSubsystem`). They cut power that pushes past a limit and clip `setTargetAngle()`. They are only as good as the angle: with no home switch, 0° is where the turret pointed at power-up, so power on pointing straight ahead. Still check the encoder direction and ticks per degree on the robot first (step 1 and 2 in `TurretAlpha`).
- **Test controls:** `TurretAlpha` uses **gamepad2**: left stick and D-pad Left/Right turn the turret (hold to move, let go to hold the angle), D-pad Up/Down change the turret power by 5% per press (default 100%), **Y / X / B** go to the center / far left (+90°) / far right (−90°) presets, **A** stops. Stick right = turn right, which is a *negative* angle, so `TurretAlpha` flips the stick sign. `MAX_MANUAL_POWER` in the subsystem is 1.0, so the OpMode's power dial is the real motor power.
- **Speeds (100%):** the manual stick power is 100% in `VisionAlpha` (and the `TurretAlpha` dial starts there; `BiobuzzTeleOp` has had no manual turret stick since issue #74). Position control (auto-align and the presets) is capped by `MAX_POWER = 1.0` in `TurretSubsystem`. Both were 50% for the first tests, then 75%. Stopping distance grows with the square of the speed, so at 100% the turret overshoots more and coasts further past a soft limit. **Not yet tested at 100%:** re-check the limit coasting (ease the stick into a limit first) and auto-align overshoot. The ±120° limits only tested safe at 50%.
- **Tested on the robot:** the ±120° limits, and `VisionAlpha` auto-align (`tx` falls toward 0 when the turret turns toward the target).
- **Test OpMode:** `TurretAlpha` (gamepad2: manual stick, hold-to-turn D-pad, power dial, Y/X/B presets, A to stop). Its header has the safe first-test order.
- **Open:** exact ring tooth count, whether the switch triggers at a different angle depending on direction of travel, and whether we go to a 360° turret.

### VisionSubsystem (`subsystems/VisionSubsystem.java`): code written, not yet tested on the robot

- **Hardware:** `limelight`, the Limelight 3A, as an Ethernet device (USB-C to USB-A into the Control Hub's USB 3.0 port). It needs about 30 seconds to boot.
- **Reads only.** It never moves the turret and has no gamepad code. The OpMode takes its answers and tells the turret what to do.
- **Target choice:** keeps only our alliance's tags (RED = tags 30-37, BLUE = tags 38-45), picks the cell holding the **highest** tag (largest `ty`, which is the raised cell), then **averages `tx` and `ty` over the visible tags of that one cell**. Averaging avoids aiming up to 6.5 in off center at a single tag.
- **Sign convention:** `getTxDegrees()` is the Limelight's: **positive = target to the RIGHT**. Turret angles are positive to the LEFT, so aiming code uses `turretAngle - tx`.
- **States:** `NO_TARGET`, `TARGET_VISIBLE`. A result older than `MAX_RESULT_AGE_MS` counts as no target.
- **Methods:** `setAlliance()`, `getAlliance()`, `update()` (once per loop), `hasTarget()`, `getTxDegrees()`, `getTyDegrees()`, `getTagCount()`, `getTargetCell()`, `getResultAgeMs()`, `isCameraConnected()`, `stop()`, `addTelemetry()`.
- **Test OpMode:** `VisionAlpha` ("Vision - Alpha"). Step 1 is camera only (watch the numbers in INIT). Step 2 is auto-align: gamepad2 Right Bumper held turns the turret to cancel `tx`, Left Stick X is manual and wins, A stops. Gamepad1 **START** switches the alliance (starts **BLUE**). It picks a new turret target only when `|tx|` is over 1 degree, so the turret's on-target check can settle. If the target is lost it holds; it does not search.
- **Aim offset (the fudge factor):** `AIM_OFFSET_DEGREES` (starts at 0.0) is added to the camera's tx inside `update()`, so `getTxDegrees()`, the "aimed" check, and auto-align all get it. **Positive = the turret aims a little more to the RIGHT, negative = more to the LEFT.** Tune it by shooting from one fixed spot: shots landing right of the hole means a more negative number, left means more positive. Change it by about 0.5° at a time (1° is about 1 inch of miss per 5 ft). It is not applied when there is no target. Telemetry shows the raw camera tx next to it.
- **Pipeline recovery (added after the first #54 robot test, where the camera stopped tracking; code written, not yet tested on the robot):** `update()` used to pick the AprilTag pipeline **once**, so if the Limelight restarted mid-run (a weak battery can dip the Control Hub's USB port), nothing picked it again and it ran on whatever pipeline it booted into. Now `checkPipeline()` runs every loop: not connected -> forget that the pipeline was picked (and count it once); connected and not picked -> pick it; otherwise every `PIPELINE_CHECK_SECONDS` (0.5) ask `getStatus().getPipelineIndex()` and call `pipelineSwitch()` if it is not `APRILTAG_PIPELINE_INDEX`. `getPipelineFixCount()` (shown as `Camera pipeline fixes` in the TeleOp and `switched back N time(s)` in the Vision telemetry) counts the drops and the switch-backs: above 0 means the camera restarted. A camera that never worked yet (still booting at INIT) is not counted. **`[CONFIRM]`:** whether a restarted Limelight really comes back on a different pipeline (the screen's `Pipeline N (wanted 0)` line will show it), and what `isConnected()` does during a restart.
- **Starting values to check on the robot:** `APRILTAG_PIPELINE_INDEX` (0, must be an AprilTag pipeline in the Limelight web page), `MAX_RESULT_AGE_MS`, `AIM_OFFSET_DEGREES`, and the two thresholds in `VisionAlpha`.
- **Tested on the robot:** the camera reads tags (pipeline 0, cell 2, 3 tags used, 5 ms old), and `tx` falls toward 0 when the turret turns toward the target, and Right Bumper auto-align works.
- **`[CONFIRM]`:** the arm can hide a pair of tags. If it hides only the left or right pair, the average shifts toward the visible side. Measure how big that error is on the real hive. Camera latency (a few frames) can also make fast turret moves overshoot a little.
- **Not in this class:** a distance calculation (the shot table uses `ty` directly, see `ShotTable`), the vertical offset from the tags to the cell opening, and searching for a lost target.

### ShotTable (`subsystems/ShotTable.java`): code written, not yet measured on the robot

- **What it is:** a plain class with **no hardware**, no `update()`, and no gamepad code. You give it a `ty` and it returns the **flywheel RPM** for a shot from there. It is not a mechanism, so its name does not end in `Subsystem`. It sits in `subsystems/` because its numbers describe the shooter `[CONFIRM]`.
- **Why `ty` and not distance:** the camera is fixed on the turret, so a closer hive shows **higher** in the view, which is a **bigger `ty`**. That makes `ty` a stand-in for distance with no lens height or camera tilt needed. **If the camera is moved or re-tilted, measure the table again.**
- **The table:** two lists in the same order, `TY_DEGREES` (smallest to biggest, which is far to close) and `FLYWHEEL_RPM`. Between two rows it draws a straight line (linear interpolation). Outside the table it **uses the nearest row and never extrapolates**. The constructor stops with a clear message if the lists are different lengths or `ty` does not strictly increase.
- **Methods:** `getFlywheelRpm(ty)`, `isInRange(ty)`, `getRowCount()`.
- **Hood wheel:** the table has one RPM per row. The hood wheel is `flywheel × HOOD_WHEEL_RATIO` when the RPM goes through `ShooterSubsystem.setTargetRpm()`. A second column is an easy later change if testing shows a fixed ratio is not enough.
- **Speed cap:** the flywheel is the 1620 RPM motor, so `FLYWHEEL_MAX_TARGET_RPM` is **1458**. **Keep every flywheel RPM at 1458 or below.** Above that the flywheel is cut off and the hood wheel (twice what you asked) is off ratio. **The farthest spot (1425 RPM) is within 33 RPM of the cap, and these rows were measured with the old 6000 RPM flywheel motor, so recheck them on the robot.**
- **Test OpMode:** `ShotTableAlpha` ("Shot Table - Alpha", gamepad1). Minimal on purpose: no drive, turret, or gate. Move the robot **by hand** and load balls into the intake. ### HiveBearingMemory (`subsystems/HiveBearingMemory.java`): code written, not yet tested on the robot

- **What it is:** a plain class with **no hardware**, no `update()`, no gamepad code (like `ShotTable`, so its name does not end in `Subsystem`). It remembers which way the hive was, on the **field**, the last time the camera saw it, so the turret can keep pointing that way when the camera loses the hive (**Pinpoint heading follow**, new in Alpha 9).
- **The math:** `hiveFieldHeading = robotHeading + turretAngle - tx` (saved every loop the camera sees the hive; `tx` is positive to the RIGHT, every other angle positive to the LEFT). When the camera loses it, `turret angle = hiveFieldHeading - robotHeading`, wrapped to -180..180 and then clipped by the turret's own soft limits. The Pinpoint's heading is zero wherever the robot sat at INIT, which does not matter, because only headings from the same match are compared.
- **Stale rule (give up, hold still):** stale once the Pinpoint says the robot has driven more than `MAX_DRIVE_SINCE_SEEN_INCHES` (**12.0**) in a straight line from where the camera last saw the hive, or more than `MAX_HOLD_SECONDS` (**5.0**) have passed. Spinning in place barely changes X and Y, so a spin never makes it stale; driving does, because driving changes the real direction to the hive and heading alone cannot see that. `[CONFIRM]` both numbers are starting guesses to tune on the robot.
- **Methods:** `remember(heading, turretAngle, tx, x, y)`, `clear()`, `hasMemory()`, `getTurretAngleDegrees(heading)`, `getDrivenInchesSinceSeen(x, y)`, `isStale(x, y, secondsSinceSeen)`, `getHiveFieldHeadingDegrees()`, the two limit getters for telemetry, and the static `wrapDegrees()`.
- **In `BiobuzzTeleOp` (Alpha 9):** `remember()` every loop the camera sees the hive and the Pinpoint is READY. In `autoAlignTurret()`, with no camera target: Pinpoint READY and memory fresh -> the turret follows the heading (with the same spin feedforward, `TURRET_FEEDFORWARD_GAIN`); stale -> holds still; no memory or Pinpoint not READY -> holds, exactly like Alpha 8. The screen line **Hive memory (Pinpoint)** says LIVE / FOLLOWING / STALE, how long ago and how far the robot has driven. **Start** on either gamepad (alliance) calls `clear()`.
- **Safety rules (Alpha 10, added after the first robot test where the turret snapped around):** (1) `BiobuzzTeleOp.checkPinpointHealth()` **clears the memory** whenever the Pinpoint has been not READY for more than `PINPOINT_GLITCH_TOLERANCE_SECONDS` (a shorter blink keeps it, see the glitch debounce under the field-centric notes), or comes back from a blink with its heading far off, or its heading jumps by more than `MAX_PINPOINT_HEADING_JUMP_DEGREES` (45, far more than a robot can turn in one 20 ms loop) in one loop. A Pinpoint that restarts (for example after a power dip) has a new heading zero, and a memory measured against the old zero would send the turret to a wrong angle. (2) If the remembered hive is **outside the turret's soft limits** (for example behind the robot), the turret **holds** (no target is set, no feedforward). Before, the target was clipped to a limit, and when the hive is behind the robot a tiny turn flips the answer between +179 and -179, which swung the turret across its whole range. `TurretSubsystem` gained `getMinAngleDegrees()` and `getMaxAngleDegrees()` so the OpMode never copies the limits. **Checked on a laptop** (follow, out of range, flip across the back, stale, and the health checks, with stand-ins for the hardware), not on the robot.
- **Not done / limits:** no search (after the robot drives to the other side of the hive, a stale memory just holds the turret, so turn the robot toward the hive until the camera sees it; the operator no longer has a turret stick or presets, issue #74); a position-based aim would need the hive's position on the field, which needs the camera mount measured (issue #39). The camera's latency of a few frames and the Pinpoint's drift both add a little error. **Checked on a laptop** (the wrap, signs and stale rules, 26 checks), not on the robot.

### VisionSubsystem lock on one cell (new in Alpha 9)

- **Convention (matches Pedro Pathing, Pinpoint and the turret):** `drive(forward, strafe, turn)`. **Forward is positive, strafe LEFT is positive, turn COUNTERCLOCKWISE is positive.** Each input is -1.0 to 1.0. The stick signs are flipped in `DriveAlpha`, with a comment saying why.
- **Wheel math:** leftFront = forward - strafe - turn, rightFront = forward + strafe + turn, leftRear = forward + strafe - turn, rightRear = forward - strafe + turn. If any wheel would pass 1.0, all four are scaled down together.
- **Methods:** `drive`, `driveFieldCentric(forward, strafe, turn, headingDegrees)`, `setSlowMode(boolean)` (slow mode; the 40% scale is `SLOW_MODE_POWER_SCALE` in the subsystem), `getTurnPower()` (how hard the robot is being told to spin, -1.0 to 1.0, + is counterclockwise, after slow mode; the TeleOp uses it to tell the turret how fast to follow the spin), `setWheelPowers` (raw, used by `drive` and the wheel tests), `stop`, `addTelemetry`. No `update()`, because there is no ongoing work.
- **Zero-power behavior:** `BRAKE` (a named constant), for precise stops. The robot is tall, so watch for tipping.
- **Two ways to drive:** `drive()` is robot-centric ("forward" is the way the robot faces). **`driveFieldCentric(forward, strafe, turn, headingDegrees)` (new, issue #54, code written, not yet tested on the robot)** is field-centric: "forward" is **away from the driver**, whichever way the robot is turned. It takes the heading as a **number** (counterclockwise positive, the Pinpoint's convention; 0 = the robot faces away from the driver), so `DriveSubsystem` never reads the Pinpoint. It turns the stick direction by **minus the heading** (`robotForward = forward*cos + strafe*sin`, `robotStrafe = -forward*sin + strafe*cos`), shrinks both together if one passes 1.0 (so a corner of the square stick keeps its direction), then calls `drive()`, so the wheel math, slow mode and the top speed are the same. Turning passes straight through. The design (starts FIELD-centric, the operator toggles the mode, forward depends on the alliance, safety rules) is in issue #54. The TeleOp uses it (session 2, below).
- **Field-centric in `BiobuzzTeleOp` ("TeleOp - Alpha 13; field-centric arrived in Alpha 11", issue #54, session 2: code written, not yet tested on the robot):** the drive **starts FIELD-centric**. **The drive toggle** (**BACK on both gamepads** since the second review of issue #63; before that it was gamepad 2's `guide` button or Left Stick Button, the `MODE_BUTTON_*_ENABLED` constants, which are gone) switches FIELD / ROBOT. **The physical Logitech MODE button cannot be used:** the coach asked for it, but the FTC SDK's `Gamepad` class has no field for it (not confirmed against the SDK javadoc, which was not reachable from the build session, but none of the SDK samples read one), and Logitech documents MODE as a hardware switch that swaps the D-pad and the left stick. The INIT screen has a **BUTTON TEST** (every button each gamepad reports, plus the left stick); if a button there ever changes when MODE is pressed, point `isDriveToggleButtonPressedOnDriverPad()` and `isDriveToggleButtonPressedOnOperatorPad()` at it. **Pressing MODE on the driver's controller while driving would swap the stick and the D-pad**, which the controls sheet warns about. **The driver's D-pad Left re-aims** ("the way the robot faces now is away from me"): an offset kept in the OpMode, **the Pinpoint is never reset** (the hive memory depends on its heading). **Which way is "away from the driver" depends on the alliance:** the blue alliance area is on the RIGHT (the blue driver faces field heading 180) and the red one on the LEFT (red faces 0). The Pinpoint's heading is zero at INIT, and our Autos never turn the robot, so after Auto the robot faces down (blue, -90) or up (red, +90). The heading the drive uses is the Pinpoint's heading plus `(robot's field heading at INIT) - (driver's forward field heading)`: blue -90 - 180 = +90, red +90 - 0 = +90 (the same, because red is blue rotated 180 degrees). The four numbers are constants per alliance. The offset is set from the alliance (START on either gamepad) in INIT and **fixed at START**: changing the alliance after START changes the camera's hive only, not which way the stick drives. D-pad Left replaces it. **Safety:** if the Pinpoint is not READY for more than `PINPOINT_GLITCH_TOLERANCE_SECONDS` (0.25 s) after START, or its heading jumps (`checkPinpointHealth`, the same check that clears the hive memory), field-centric switches itself off and the drive is robot-centric; the screen says why; it does NOT switch itself back on (a restarted Pinpoint has a new zero) until the drive toggle or D-pad Left. **Glitch debounce (added after the first robot test, where a weak battery made the Pinpoint blink and field-centric kept switching off; code written, not yet tested on the robot):** a gap shorter than 0.25 s is a glitch, not a restart. `checkPinpointHealth()` does not latch and does not clear the hive memory; with `HOLD_LAST_HEADING_DURING_GLITCH` (true) the drive keeps field-centric using the last good heading (`getPinpointHeadingForDrive()`); when the Pinpoint is READY again its heading must be within `RESUME_MAX_HEADING_CHANGE_DEGREES` (20) of the last good heading (otherwise it probably restarted, so it latches off like a long gap). A restart that happens while the robot already faces its INIT direction changes nothing, so missing it is harmless. The screen shows `Pinpoint glitches (came back by themselves)` with the count and the longest gap, which is the clue for a weak battery. The old rule latched on the first not-READY loop. `DriveAlpha` now has the same debounce (same constants), and its screen shows the same two lines. **Still open after a second robot test:** `DriveAlpha` (old rule) still dropped to robot-centric with a **fresh battery**, only later, so a weak battery is not the whole story. The drop log (next bullet's class, `PinpointSubsystem`) is there to find the real cause. The screen shows `DRIVE MODE` under the alliance line. Assumptions to confirm: blue drivers stand on the right and red on the left, and the robot is not moved between Auto and INIT. The turn stick is the same in both modes, so the turret's spin feedforward is unchanged.
- **Checked on a laptop (not on a robot):** the real `BiobuzzTeleOp`, `DriveSubsystem`, `HiveBearingMemory` and `ShotTable` compile against stand-ins for the SDK and the other subsystems, and a simulation of the robot's motion from the real wheel powers passed 29 checks as a BLUE and a RED robot: at six turn angles the stick's forward goes to field 180 (blue) or 0 (red) and left goes 90 degrees to the driver's left, an alliance fixed in INIT is used, an alliance change after START and a re-aim survive correctly, MODE (both buttons) toggles, and both safety cases (Pinpoint not READY, heading jump) fall back to robot-centric and stay there until MODE or D-pad Left.
